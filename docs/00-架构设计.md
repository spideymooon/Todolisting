**结论：全新项目（Greenfield），无历史包袱，可自由选型。**

| 检查项 | 结果 |
| --- | --- |
| 工作区内容 | 空目录，无既有代码 |
| Node.js | v22.22.2 + npm 10.9.7 ✅ |
| Rust | 1.88.0（msvc target）⚠️ |
| MSVC 链接器 / VS BuildTools | **缺失** ❌ |
| WebView2 Runtime | 已安装（153.0.4234.32）✅ ~~v0.4 误记为未安装，v0.5 复查纠正~~ |
| 操作系统 | Windows 10 22H2 (10.0.19045) ✅ |

**关键约束推导：**

1. **Tauri 方案被排除**：Tauri 需要 MSVC 链接器编译 Rust 后端，且依赖 WebView2 运行时。当前两者均缺失，改用 Tauri 需用户先安装 VS Build Tools（数 GB）+ WebView2 Runtime，且后续每次构建都强依赖该工具链。
2. **任何需要 node-gyp 编译的原生模块都有风险**：已实测 `better-sqlite3` 能下载到 Node ABI 的预编译包并正常工作，但它**在 Electron 下需要针对 Electron ABI 重新 rebuild**（`@electron/rebuild` 又要走 MSVC）——这正是要规避的坑。
3. **实测选定 `node-sqlite3-wasm`**：SQLite 编译为 WASM，**纯 JS 依赖、零编译**，却提供**真实的 `.sqlite` 文件读写**（实测生成 8192 字节标准 SQLite 文件）与同步 API。既满足 §18「SQLite 本地保存」，又绕开全部原生编译风险。

## 1. 技术栈选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 应用外壳 | **Electron 44.4.1**（实现时取 latest 稳定线） | 对环境零额外依赖；`transparent + frame:false + alwaysOnTop + skipTaskbar` 多窗口是桌面小组件的成熟方案；原生托盘 / 通知 / 全局快捷键 / 开机启动 API 齐备；UI 保真度最高，能满足 §14 的设计要求 |
| 构建 | **electron-vite 5** + Vite 7.3 | 主进程 / preload / 渲染进程三端统一构建，HMR 快 |
| UI 框架 | **React 19 + TypeScript 5.9** | 组件化适配「同一套设计语言跑主窗口 + 4 种小组件」 |
| 样式 | **原生 CSS + 设计 Token 变量表**（`tokens.css` / `app.css`） | 见下方说明 |
| 动效 | **纯 CSS transition / keyframes** | 本阶段动效都是时长+缓动的确定性变化，引入 framer-motion 属于净增体积 |
| 状态 | **Zustand 5** | 极轻，无需 Redux 那套样板 |
| 拖拽 | **@dnd-kit/core**（只用 core，不用 sortable） | 体积小；列内不需要排序（拖拽只改 `due_date`/`status`，不改顺序），sortable 是多余依赖 |
| 数据库 | **node-sqlite3-wasm** | 见 §0.3。真实 `.sqlite` 文件 + 零原生编译 |
| 主进程架构 | 分层 + Repository / Service 模式（§26 推荐目录） | 通知逻辑与 UI 彻底解耦（§4 明确要求） |

### 实现时的三处选型调整（v0.4 记录）

| 原计划 | 实际采用 | 原因 |
| --- | --- | --- |
| Tailwind CSS v4 | **原生 CSS 变量表** | 设计规范已经把整套 token 写成了 CSS 变量（颜色 / 圆角 / 阴影 / 字号），本来就等价于一份 CSS 变量样式表。而本项目的样式全是像素级定制（44px 捕获条、10px 卡片圆角、8px 卡片间距），Tailwind 的收益在「快速试没定下来的设计」——这里设计早就定死了。去掉它还少一层构建与 preflight 冲突风险 |
| Radix UI Primitives | **当前未引入** | 本阶段只用到一个自制浮层（卡片 `···` 菜单）。为一个菜单引 Radix 不划算，等做到设置页复杂表单 / 日期选择器时再引 |
| Motion (framer-motion) | **纯 CSS** | 同上，本阶段动效无需 JS 编排 |

> 这三条都是**减依赖**方向的调整，不影响任何设计规格。把 Tailwind 换成 CSS 变量表，产出的 CSS 是 17KB（未压缩），比 Tailwind 运行时更小。

### 为什么不用 Tauri

**Tauri 的取舍**：产物约 10MB、内存占用低，是本项目在「无环境约束」下的更优解。排除它的真实原因是**缺 MSVC 链接器**（WebView2 运行时已装，v0.4 曾误记为缺失，v0.5 已勘误）。**如果后续愿意安装 VS Build Tools，可以平滑迁移**——因此本设计把业务逻辑全部放在与运行时无关的 `src/main/core` 层，UI 层通过 preload 契约通信，迁移时只需替换壳。

## 3. 数据库设计

### 3.1 时间约定（§18 要求「统一格式 + 正确处理时区」）

这是最容易埋坑的地方，明确约定：

| 字段类型 | 格式 | 说明 |
| --- | --- | --- |
| `created_at` / `updated_at` / `completed_at` / `sent_at` 等**时刻** | ISO 8601 **UTC**，如 `2026-09-18T01:00:00.000Z` | 绝对时刻，跨时区安全 |
| `due_date` / `anchor_date` 等**日历日** | `YYYY-MM-DD` **本地日期** | 「9月20日截止」是日历概念，不是时刻 |
| `due_time` / `reminder_time` | `HH:mm` **本地时间** | 用户输入的钟点 |

**为什么 `due_date` 不用 UTC？** 若用户设定「2026-09-20 截止」，UTC 存储会在时区换算后变成 09-19，导致「今天到期」判断错位一天。日历日必须按本地日历语义存储。由此引入一个**冗余字段** `due_at_utc`，由 `due_date + (due_time ?? '23:59')` 按**当前时区**折算而来，仅用于排序与范围查询，时区变更时随重算更新。

## 4. 提醒系统设计（§4 + §23）

### 4.1 核心计算函数（纯函数，易测）

```
nextReminderAt(task, nowUtc, tz) -> { atUtc, reason } | null

  // ① 短路守卫
  if task.deleted_at !== null            → null   // 已删除
  if task.status === 'completed'         → null   // §5 已完成不再提醒
  if !task.reminder_enabled              → null   // 未开启提醒
  if !task.due_date                      → null   // 无截止日 = 无提醒锚点
  if channels(task).length === 0         → null   // 两个通道都关闭

  // ② 基准：截止日往前推 N 天，再取 reminder_time
  remindDate      = task.due_date - task.reminder_days   // 本地日历日减法
  scheduledLocal  = remindDate @ task.reminder_time       // 本地时区
  deadlineLocal   = task.due_date @ (task.due_time ?? '23:59')

  // ③ 收敛：提醒不得晚于截止
  if scheduledLocal > deadlineLocal → scheduledLocal = deadlineLocal

  // ④ 过去时刻的处理（需求空白，见《02-需求评审与改进建议》问题 3）
  if scheduledLocal <= now:
       if deadlineLocal >= now   → 返回 now + 30s（立即补发，仅一次）
       else                      → 按「逾期策略」：默认不再提醒，返回 null

  return scheduledLocal.toUtc()
```

**示例校验（需求文档原文）**：截止 `2026-09-20 18:00`、提前 `2` 天、提醒时间 `09:00` → `remindDate = 2026-09-18` → 触发 `2026-09-18 09:00` ✅

### 4.2 幂等与防重复（§23）

四道防线叠加：

| # | 机制 | 防的场景 |
| --- | --- | --- |
| 1 | `plan_key = taskId\|type\|scheduledAt` 上的 **UNIQUE 约束** | 任何并发/重复写入，数据库层直接拒绝 |
| 2 | 发送前 **`INSERT OR IGNORE` 占位**（status=pending），只有抢占成功才真正发送 | Scheduler 被重复触发、多窗口同时 tick |
| 3 | `app.requestSingleInstanceLock()` 单实例锁 | §23 明确点名的「程序重复启动」 |
| 4 | 启动时**崩溃恢复**：`pending` 且 `scheduled_at` 超过 5 分钟的记录 → 标记 `failed` 并允许重试，而不是重发 | 进程在发送中途被杀死 |

**重新计算的触发时机**（§23 要求）：修改 `due_date` / `reminder_days` / `reminder_time` / `notification_type` / `reminder_enabled` 或**完成任务**时，统一调用 `notificationService.replan(taskId)`：

```
replan(taskId):
  1. 事务内把所有 status='pending' 的日志改为 'cancelled'
  2. 重新跑 nextReminderAt()
  3. 有新时刻 → 用新的 plan_key 插入 pending（因 plan_key 不同，不会与历史冲突）
  4. 已 sent 的历史记录保留，作为「已提醒过」的审计痕迹
```

这既满足「修改后重新计算」，又满足「同一个提醒不重复发送」——因为旧计划作废了，新计划的 key 与旧的不同。

### 4.3 调度器（Scheduler）

**不用 `setTimeout` 长定时**。原因：Windows 睡眠/休眠后定时器会漂移甚至丢失，长 setTimeout 会在唤醒后一次性补发一堆。

```
每 30 秒 tick 一次：
  1. 取所有 pending 且 scheduled_at <= now + 5s 的日志
  2. 逐条走幂等发送流程
另外监听：
  - powerMonitor 'resume'      → 立即 tick（睡眠唤醒）
  - powerMonitor 'unlock-screen' → 立即 tick
  - 系统时间变更（tick 内对比上次 now，跳变 > 2min 则强制全量重算）
```

30s 的精度对「提前 N 天 + 定点 HH:mm」的提醒完全够用，且开销可忽略。

## 5. 通知分发

### 5.1 Notification Service（统一出口）

`notification.service.ts` 是所有通知的唯一出口，`ui/` 与 `task/` 都不直接碰通知：

```
dispatch(log):
  channel = log.notification_type
  if channel in ('desktop','both') → windowsNotifier.send()   // 失败不阻塞
  if channel in ('wechat','both')  → pushplus.send()          // 失败记录但不抛出
  汇总结果 → 更新 notification_logs.status / sent_at / error_message
```

**离线优先（§19）**：微信通道失败**绝不影响**任务创建/完成。`send()` 全程 try/catch，任何异常都只落到 `notification_logs.error_message`，并提供「重新发送」入口。

### 5.2 Windows 原生通知（§5）

- 用 Electron `Notification`，设置 `toastXml`/`appId` 保证在 Win10 通知中心正常显示。
- 文案按 §5 模板：标题 `📌 任务即将到期`，正文 `「提交周报」\n距离截止还有 2 天`。
- `notification.on('click')` → 主进程 `mainWindow.show() + focus()`，再通过 IPC 发 `task:locate` 携带 `taskId`，前端滚动定位并高亮 1.5 秒。
- **前置条件**：通知的点击回调只有在应用进程存活时才有效。所以托盘常驻（§22）是通知功能的硬依赖，两者必须一起交付。

### 5.3 PushPlus 微信提醒（§6）

```
POST https://www.pushplus.plus/send
{
  "token":    <从 credential.service 读取>,
  "title":    "📌 任务即将到期",
  "content":  "「提交周报」\n距离截止还有 2 天\n截止：2026-09-20 18:00",
  "template": "markdown",
  "channel":  "wechat"
}
```

**Token 安全（§6 硬性要求，不得硬编码）：**

| 优先级 | 来源 | 用途 |
| --- | --- | --- |
| 1 | `safeStorage.encryptString()` → `credentials.bin`（Windows 下走 **DPAPI**，密钥绑定当前用户账户） | 正常运行时的唯一来源 |
| 2 | 环境变量 `PUSHPLUS_TOKEN` | 仅开发调试用覆盖 |
| 3 | ❌ 代码 / 仓库 | **禁止**；`.gitignore` 排除 `credentials.bin` |

界面上只显示掩码 `**************`，不回显明文。

**健壮性设计：**
- 超时 10s；重试 3 次，退避 1s / 5s / 15s（仅对网络错误与 5xx 重试，4xx 直接判定为 Token 错误不重试）
- 本地限流：两次发送间隔 ≥ 3s（PushPlus 免费版有频率限制）
- Token 无效 / 网络失败 → 界面明确提示「微信提醒发送失败，请检查 PushPlus Token 或网络连接。」
- 提供 **「发送测试通知」** 按钮（§6），发送 `TodoList 测试通知 / PushPlus 微信提醒配置成功。`

## 6. 桌面小组件架构（§9–§12）

### 6.1 一个组件 = 一个独立 BrowserWindow

```ts
new BrowserWindow({
  width, height, x, y,
  frame: false,          // §12 无边框
  transparent: true,     // §12 半透明
  alwaysOnTop: true,     // §10.1 置顶
  skipTaskbar: true,     // 不占任务栏（像桌面的一部分）
  resizable: true,
  hasShadow: false,
  backgroundColor: '#00000000',
  webPreferences: { preload, contextIsolation: true, nodeIntegration: false }
})
```

### 6.2 透明度的实现方式（关键决策）

**用 `win.setOpacity(0.2 ~ 1.0)`（原生窗口级透明度），而不是 CSS `rgba` 背景。**

原因：CSS 半透明只能让卡片背景变淡，卡片里的文字、图标仍然是 100% 不透明 —— 视觉上会出现「文字浮在半透明色块上」的廉价感。`setOpacity` 让整个窗口（含文字）真正半透明融合进桌面，才是 §12 要的「像桌面的一部分」。两种方式都保留为可选项，默认走原生。

### 6.3 无边框窗口的移动与缩放

Windows 上 `transparent: true` 会禁用系统的窗口边缘缩放热区，必须自己实现：

- **移动**：CSS `-webkit-app-region: drag` 拖拽区（避开按钮）
- **缩放**：渲染层右下角/四边放 8px 透明热区，`pointerdown` 后监听全局 `pointermove`，换算成增量通过 IPC 调 `win.setBounds()`；`pointerup` 结束并持久化
- **交互区**：所有按钮显式 `-webkit-app-region: no-drag`

### 6.4 位置持久化与多屏兜底（§10.5 多组件，§29 要求重启恢复）

```
保存：'moved' / 'resized' 事件 → debounce 500ms → 写入 widgets 表
      （含 x, y, width, height, display_id）

还原：1. 查 display_id 对应的显示器是否还存在
      2. 不存在（拔掉了副屏）→ 落到主显示器
      3. 用 screen.getDisplayMatching(bounds).workArea 做 clamp
         ，确保窗口完整落在工作区内（不跑到屏幕外、不被任务栏遮住）
```

这是需求没提但**必须做**的：不做兜底，用户拔掉外接显示器后小组件会永久消失，且无法拖回来。

### 6.5 悬停显示操作（§11）

小组件默认只有内容，**鼠标进入才淡入**右上角一枚极小的 `···` 按钮（`opacity 0 → 1`，200ms），点开是菜单：设置 / 透明度 / 置顶 / 尺寸 / 关闭。同时支持**右键菜单**直达同样入口。绝不常驻显示一排按钮。

### 6.6 四种组件的内容规格

| 组件 | 内容 | 数据源 | 建议默认尺寸 |
| --- | --- | --- | --- |
| 今日待办 | 日期标题 + 任务列表（○ 未完成 / ✓ 已完成）+ `2 / 3 完成` | `due_date = 今天` 或「今天到期 + 逾期未完成」 | 300 × 240 |
| 即将到期 | 按「今天 / 明天 / N 天后」分组，仅列未完成 | `due_at_utc` 在 [now, now+7d] | 300 × 260 |
| 今日进度 | 圆环 75% + 文案「今日完成率」 | 今日任务完成比 | 220 × 220 |
| 快速添加 | 单个输入框 `添加任务……`，Enter 即建 | 直连 task.service | 320 × 64 |

### 6.7 多窗口数据同步

主窗口、快速添加窗、多个小组件窗口共享同一份 SQLite。通过主进程 `core/task` 层统一写入，写成功后广播 IPC 事件 `tasks:changed`，所有窗口订阅后增量刷新。**绝不让渲染进程各自缓存并写库**，避免多窗口数据不一致。

## 7. 全局快捷键与快速添加（§15）

```
Ctrl + Shift + Space
    ↓  主进程 globalShortcut 拦截
呼出 quick-add 窗口（320×64，无边框，居中，skipTaskbar，alwaysOnTop）
    ↓  自动聚焦输入框
输入任务 → Enter
    ↓  IPC → task.service.create({ title, due_date: 今天 })
    ↓  广播 tasks:changed
窗口立即隐藏（无动画延迟，保持 Raycast 般的干脆）
```

细节：`Esc` 隐藏；窗口 `blur` 时自动隐藏；如果全局快捷键被其他软件占用，`globalShortcut.register` 返回 `false` —— 此时向用户提示并提供「更换快捷键」入口（§15 要求「冲突时选择合理替代方案」）。

### 7.1 应用内捕获条（v0.3 新增，与全局快捷键互补）

主窗口内的常驻捕获条（《01-UI设计规范》§3.4）与全局快捷键是**两条互补路径**：

| | 捕获条 | 全局快速添加窗 |
| --- | --- | --- |
| 触发 | 打开主窗口即聚焦；应用内 `Ctrl + N` 聚焦 | `Ctrl + Shift + Space` 全局 |
| 适用 | 已经在用这个应用 | 应用未打开 / 被遮挡 |
| 落点 | chip 显示并可控 | 同上，默认今天 |

- **自动聚焦的实现位置**：`windows/main-window.ts` 在窗口 `show` / `focus` 后发一次 `capture:focus` 事件给渲染层；**由渲染层决定是否真的聚焦**（因为只有渲染层知道当前是否打开了编辑器弹层、是否已有草稿）。主进程不强制 `webContents.focus()` 抢占。
- **快捷键释放**：`Esc` 在捕获条内被按下时，渲染层 `blur()` 并把焦点交还页面根节点 —— 这是解决「全局快捷键被输入框吞掉」的关键，因为自动聚焦让捕获条**默认就持有焦点**。
- 捕获条**不注册任何全局快捷键**，只走应用内 `before-input-event` / React 键盘处理，避免与系统级快捷键冲突。

## 8. 系统托盘与开机启动（§21 / §22）

- **托盘菜单**严格按 §22 结构，其中「今日任务：3」由 `tasks:changed` 事件动态更新 tooltip 与菜单文本。

## 9. IPC 契约（preload 白名单）

`contextIsolation: true` + `nodeIntegration: false`，渲染进程只能通过 preload 暴露的白名单调用：

```ts
window.api = {
  task: {
    list(filter): Promise<Task[]>
    create(input): Promise<Task>
    update(id, patch): Promise<Task>
    toggle(id): Promise<Task>
    remove(id): Promise<void>
    search(query, filter): Promise<Task[]>
    capture(rawText, defaultTarget): Promise<CaptureResult>  // ★ 捕获条唯一入口
    moveTask(id, target): Promise<Task>                      // 看板拖拽原子操作
  },
  settings: { get(), set(patch), testPushPlus() },
  widget:   { list(), create(type), update(id, patch), remove(id), close(id) },
  data:     { export(), import(), backup(), restore(), revealPath() },
  on:       { tasksChanged(cb), locateTask(cb), themeChanged(cb) },
  system:   { openMainWindow(), quit() }
}
```

> `capture(rawText, defaultTarget)` 的设计约束：**渲染层只传原始文本 + 默认落点，绝不传已解析的字段**。主进程用 `src/shared/capture-parse.ts` 的同一份纯函数重新解析，以主进程结果为准。这样解析逻辑只有一个权威版本，渲染层无法（也不会）写入错误日期。
>
> 解析器是纯函数，可直接单测 —— 与 `core/reminder/reminder.engine.ts` 同一种测试策略。

## 13. 附录：UI 方向修正（v0.2，2026-09-17）

依据《Workbuddy-UI方向修正-左侧导航右侧Kanban.md》与参考图 `1.png` / `2.jpg` 修订。**本节只改 Renderer/UI 层，以下所有主进程与数据库设计（§3–§6）维持不变。**

### 13.1 修正结论

> **不是取消 Sidebar，而是：左侧导航 Sidebar + 右侧 Kanban 看板。**

Sidebar 是一级导航（今天 / 看板 / 即将到期 / 全部任务 / 已完成 / 设置），看板是其中一个**一级页面**，不是全局形态。

### 13.2 看板三列 = 现有字段的三个查询视图（零架构改动）

| 列 | 条件 |
| --- | --- |
| 待办池 | `due_date IS NULL OR due_date > 今天 AND status='pending'` |
| 今日待完成 | `due_date <= 今天 AND status='pending'` |
| 今日已完成 | `due_date = 今天 AND status='completed'` |

> **v0.4 修正**：原 `待办池 = due_date IS NULL` 会让「明天到期」的任务三列都进不去 —— 而「明天 xxx」正是捕获条最常用的一句。改为「未排入今天」后，看板才是所有未完成任务的完整视图。详见《01-UI设计规范》§5.1。

四条拖拽语义全部落回现有字段，无需新增任何业务概念：

```
待办池 → 今日待完成 : due_date = today          → 触发 reminder replan
今日待完成 → 今日已完成 : status='completed'     → 取消未发提醒
今日已完成 → 今日待完成 : status='pending'       → 重新计算提醒
今日待完成 → 待办池 : due_date = null            → 取消提醒（无截止日无提醒锚点）
```

`task.service` 需要暴露一个**原子操作** `moveTask(taskId, target: 'pool'|'todayPending'|'todayDone')`，内部在同一个事务里改字段 + 调 `notificationService.replan()`。拖拽 UI 只调用这个原子操作，不自己拼字段 —— 这样提醒重算永远和字段变更在同一事务，不会出现「列变了但提醒没重算」的中间态。

**逾期任务**：`due_date < 今天 && status='pending'` 的任务自动浮到「今日待完成」列顶部，卡片带红色 `⚠`。

### 13.3 标签提前到 P1（唯一的范围变更）

`tags` / `task_tags` 两张表在 §3.2 本就预留，本次只是**提前启用**，不改表结构。原因：看板卡片的第二行元信息（彩色圆点 + 标签名）是参考图 `1.png` 视觉的关键组成，没有它卡片会显得空。

明确**不引入**（来自参考图但会波及业务层）：

| 参考图元素 | 不做的理由 |
| --- | --- |
| 「进行中」第三种 status | 提醒引擎、防重复通知、完成判断都假定两态；引入第三态是业务层改动，非 UI 改动 |
| 子任务进度 `0/2` | 需要子任务表 + 级联完成逻辑，Phase 6 再议 |
| 优先级 `P4`（第四级） | 保持 §3 三级；若要支持只需扩 CHECK 枚举一行 |
| Dashboard 统计卡 | §九 明确禁止 |

**四道防重复防线的落点**：

1. `notification_logs.plan_key` UNIQUE —— 数据库层物理拒绝（意图时刻进 key，replan 才能算出稳定 key）；
2. `upsertPlan()` 幂等语义 —— sent 永不重排，cancelled/skipped 可复活，planned 只改执行时刻；
3. `app.requestSingleInstanceLock()` —— 重复启动直接退出；
4. 崩溃恢复 —— planned 且过点 5 分钟视为进程中断，标 skipped 并复活重排；`powerMonitor` 唤醒/解锁或时间跳变 > 2 分钟触发全量重排。

**实现中修掉的 3 个真实问题：**

1. **收敛时刻未生效**（测试捕获的真 bug）：「提前提醒 09:00 晚于截止 08:00」时原返回 09:00 而非收敛后的 08:00，因 `atSchedule()` 传的是收敛前的时刻。修复后由测试锁定。
2. **`recent()` 排序不确定**：同一次 replan 插入的多条记录 `created_at` 完全相同，只按它排序会让「最近一条」随机变。改为 `ORDER BY created_at DESC, rowid DESC`。
3. **截图期发现的时序问题**：设置页首帧取数失败会被 `catch` 静默吞掉、显示全零状态（截图窗口只存活 4 秒、15 秒轮询来不及重试时出现）。长驻使用下无影响，但已确认 15 秒轮询能把状态拉回正确值。

**编辑器与通知的联动**：双击卡片 / Enter / 菜单「编辑任务」进入弹层；改动提醒字段走 `task.service.update` → 同事务 replan；点击 Windows 通知 → `openAndLocate` → 渲染层 `locate()` 高亮 2.2 秒（加载中的窗口等 `did-finish-load` 再发，避免事件静默丢失）。

  - `appId: com.desktoptodo.app`（与 AUMID 一致，通知归组正确）；`productName: TodoList`；版本号 0.1.0 → **1.5.0**。
  - `files: ["out/**"]`——生产依赖 node_modules 由 electron-builder 自动收集（主进程 bundle 外部化了 dependencies）。
  - **`asarUnpack: ["**/node_modules/node-sqlite3-wasm/**"]`**——WASM 文件不能从 asar 内以普通 fs 读出，必须解包到 `app.asar.unpacked/`（已确认产物含 node-sqlite3-wasm.wasm）。
  - `win.icon: build/icon.ico`（§18 的九档品牌 ICO，自动内嵌 exe）；NSIS 目标，`oneClick:false` + `allowToChangeInstallationDirectory:true`（可选安装目录）+ 桌面快捷方式，`shortcutName: TodoList`。
  - 输出目录 **`dist/`**（`release/` 被之前一次失败构建的文件锁占住删不掉）。
- 打包命令 `npm run dist` = `electron-vite build && electron-builder --win`。中国网络需 `ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/`（GitHub 下载 NSIS 资源 502）。

### 19.2 打包态行为确认（代码已就位，无需改动）
- AUMID：`app.isPackaged` 时设 `com.desktoptodo.app`（§18.5 的 dev 分支与 `ensureDevStartMenuShortcut()` 自动跳过，快捷方式由安装器创建）。
- 数据库：userData 随 productName 变为 `%APPDATA%\TodoList`，首启建库 + 种子数据，与 dev 数据隔离。
- 自定义存储目录 `db-location.json` 存于新 userData，逻辑不变。

### 19.3 踩坑
- **EBUSY unlink app.asar**：Defender 实时扫描刚写入的 asar 导致无法覆盖/删除，且工作区安全删除策略拦 `Remove-Item`——换输出目录绕过，别恋战。
- **打包版"秒退 exit 0"假象**：会话环境强注入 `ELECTRON_RUN_AS_NODE=1`，TodoList.exe 被当纯 Node 启动（`bad option: --enable-logging` 是 Node 报错口吻）。清掉该变量后 16s 持续运行、窗口/看板/任务栏品牌图标全部正常。**打包冒烟测试必须剔除这个环境变量**。

### 19.4 产物
- `dist/TodoList Setup 1.5.0.exe` —— NSIS 安装包（约 100MB 级，含 Chromium）。
- `dist/win-unpacked/TodoList.exe` —— 免安装绿色版，可直接运行验证。
- 打包冒烟：subprocess 启动 win-unpacked 版 16s 存活、截图确认主窗与三列看板渲染正常、任务栏为品牌图标（安装器快捷方式 AUMID 链路在真实安装后生效）。
