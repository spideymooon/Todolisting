# 需求评审与改进建议

> 对应需求文档末尾要求：「如果发现需求存在明显的产品问题、交互问题、技术风险或者更好的实现方案，**不要机械执行**。请先指出问题，并给出更合理的方案，再实施。」
>
> 以下 10 条是逐条评审后真正会出问题的点，按严重程度排序。每条都给出**默认方案**，如果认可就按默认实现，无需逐条回复。

---

## 问题 1 ⭐️ 严重：「提前 N 天提醒」在临近截止时永远不触发

**现象**：需求 §3 的例子是「截止 2026-09-20，提前 2 天 → 09-18 提醒」。但如果用户在 **09-19** 才创建任务「明天交报告」，设了提前 2 天 —— 提醒时刻 `09-18 09:00` 已经是**过去**。按字面实现，这个任务**永远不会提醒**。

**这是真实高频场景**：用户往往是「快到截止了才想起来记录」，此时提前 N 天的语义天然失效。

**更合理的方案（三层兜底）**：

1. **收敛**：提醒时刻不得晚于截止时刻（`提前7天` + 明天截止 → 收敛到截止时刻）
2. **补发**：算出的提醒时刻已过去，但**任务尚未逾期** → 立即补发一次提醒（`now + 30s`），且只补一次
3. **逾期策略**：任务已逾期 → 默认**不再提醒**（因为「已逾期」在列表和小组件里已经醒目展示，再推送就是骚扰）。提供开关：`逾期后补提醒一次 / 不再提醒 / 每天提醒`

## 问题 2 ⭐️ 严重：重复任务会淹没「已完成」列表

**现象**：§8 说「完成任务后自动生成下一次任务」。那么「每周写周报」这个任务，一年会在「已完成」里留下 **52 条几乎同名**的记录。用户翻看历史时会崩溃，且「已完成」视图失去意义。

**根因**：需求把「重复规则」和「任务实例」混为一谈。

**更合理的方案 —— 母版 / 实例分离**：

```
recurrence_rules  ← 规则（每周一 09:00）
      ↓
tasks(is_template=1)  ← 母版，只存规则，不出现在任何列表
      ↓ 按规则展开
tasks(series_id=...)  ← 实例，用户看到和勾选的就是它
```

配套规则：
- **已完成视图默认只保留最近 30 天的重复实例**，更早的折叠为「周报 · 本周第 N 期（共 M 期）」
- 重复实例的 `reminder_*` 从母版继承，可单次覆盖
- 修改母版规则时，询问「仅本次 / 本次及以后」

数据库已按此预留（`recurrence_rules` + `series_id` + `is_template`），MVP 不实现也不会返工。

## 问题 3 ⭐️ 严重：开机静默启动 + 无小组件 = 用户找不到应用

**现象**：§21 要求「开机启动后不弹出主窗口，只在托盘运行」。但如果用户：装了应用 → 勾了开机启动 → 没添加任何小组件 → 开机后……**屏幕上什么都没有**。托盘图标被折叠在任务栏溢出区的话，用户会认为应用没启动，甚至重复安装。

**更合理的方案**：

1. **首次**以「隐藏模式」启动且用户从未打开过主窗口时，发一条 Windows 通知：「TodoList 已在托盘运行，点击打开主界面」。**只发一次**（用 `settings` 里的 `onboarded_hidden_start` 标记）
2. 托盘图标提供「显示今日待办」一键添加小组件（§22 已有此菜单项，但功能上要能真正兜底）
3. 设置页的「开机启动」开关下方，明确灰字提示「启动后将在系统托盘运行，不弹出主窗口」

## 问题 4 ⭐ 中等：逾期任务到底还提不提醒？需求没定义

**现象**：§4 只定义了「下一次提醒时间」的计算，完全没提逾期。结果就是：逾期任务要么被无限提醒（骚扰），要么被静默（用户丢事）。

**更合理的方案**：在设置页提供「逾期提醒」三选一，默认值：

> **逾期当天补提醒一次，之后不再提醒**

理由：逾期当天用户最需要被提醒；连续多天推送同一条已经知道的事，是通知疲劳的主要来源。

## 问题 5 ⭐ 中等：通知的「同一条只发一次」和「修改后重新计算」需要区分「计划的身份」

**现象**：§23 要求「同一个任务、同一个提醒时间只能发一次」，同时又要求「用户改了截止日期/提前天数/提醒时间要重新计算」。这两条如果实现得简单粗暴会互相打架：改了时间后，新计划因为和旧计划「时刻不同」能发出（对），但如果用户**改回去**（`09-18 09:00` → `09-19 09:00` → 又改回 `09-18 09:00`），按「只发一次」的朴素实现，第二个 `09-18 09:00` 会被永远拦住，用户再也收不到提醒。

**更合理的方案**：引入「计划版本」——旧计划在重新计算时被显式标记为 `cancelled`，只有 `pending` 状态的计划参与去重。幂等键 `taskId|type|scheduledAt` 上加 UNIQUE 会让「改回去」的场景插入失败，因此：

```
去重判定 = plan_key 相同 且 已有记录状态 ∈ (pending, sent)
  → 拦截
plan_key 相同但旧记录 status = cancelled
  → 允许重新插入新计划
```

也就是**幂等键查重时必须带上 status 条件**，而不是纯靠 UNIQUE 约束。UNIQUE 约束仍需保留（防并发双写），冲突时回退到上面的判定逻辑。

## 问题 6 ⭐ 中等：`notification_type` 用单字段表达「两者同时开启」不够用

**现象**：§7 要求「每个任务可选：桌面提醒 ON/OFF、微信提醒 ON/OFF、两者同时开启」。而 §3 的字段清单里只有**一个** `notification_type` 字段。用 `desktop|wechat|both` 三个枚举值能表达当前 4 种组合，但如果将来加第三种通道（邮件、飞书），枚举会爆炸。

**方案**：MVP 保留 `notification_type` 枚举（简单、够用、符合 §3 字段清单），但在 Repository 层做一层 `channels(task) -> Channel[]` 的映射函数。未来加第五个通道时，只需把列迁移为 `notify_desktop` / `notify_wechat` 两个布尔列 —— 调用方代码不变。**不提前抽象，只预留出口。**

## 问题 7 ⭐ 中等：`Space` / `Delete` / `Enter` 快捷键会与按钮焦点冲突

**现象**：§16 要求 `Space` 完成、`Delete` 删除、`Enter` 编辑。但需求同时要求每个任务悬停时显示「完成 / 编辑 / 删除」按钮 —— 用户用 Tab 或鼠标点过按钮后，焦点落在按钮上，此时按 `Space` 触发的是**按钮点击**，而不是「完成任务」；`Delete` 也会被输入框吞掉。

**更合理的方案**：
- 快捷键只在**任务列表获得焦点、且焦点不在 input/textarea/button** 时生效（`e.target` 白名单判断）
- 按钮统一加 `tabIndex={-1}`，让其不进入 Tab 序列，鼠标点击仍然正常
- 删除用 `Delete`，但在 macOS 风格下也支持 `Backspace`；删除后弹 5 秒「已删除 · 撤销」toast 而不是确认框（更符合 §28 的「快」）
- 冲突兜底：任务编辑器打开时，列表快捷键全部挂起

## 问题 8 ⭐ 中等：小组件的「20% 透明度」几乎不可用

**现象**：§10.2 规定透明度范围 20%～100%。20% 的不透明度下，一个 14px 的中文文字对比度约 1.2:1 —— 完全无法阅读，用户会以为是渲染 bug。

**更合理的方案**：
- 滑块范围保留 20%～100%（尊重需求），但**在 20%～40% 区间给出实时预览**，并让 UI 自身保持可读：即「卡片底板 20%，文字最低 65%」的**双通道透明度**
- 用原生 `setOpacity` 实现整体透明时，文字会一起变淡 —— 所以提供两种模式：
  - **整体透明（默认）**：整窗 `setOpacity`，追求「融进桌面」
  - **仅底板透明**：窗口 100% 不透明，卡片背景用 `rgba`，文字保持清晰
- 预设值 20 / 40 / 60 / 80 / 100 保留（§10.2 要求），另加滑块

## 问题 9 ⭐ 轻微：「点击通知打开 TodoList」在应用退出时不可能实现

**现象**：§5 要求点击通知后打开应用并定位任务。但 Windows 原生 toast 的点击回调依赖进程存活 —— 应用退出后，通知（若已发出并留在通知中心）被点击时不会唤起应用。

**方案**：
- 明确「托盘常驻」是通知功能的前置条件（§22 托盘的优先级因此高于 §5 通知，虽然文档顺序相反）
- 通知发出后若应用退出，残留通知点击无响应属于可接受行为，但要在文档中说明，不做「协议注册唤起」的过度设计（那需要写注册表 + 自定义 URI scheme，对一个个人待办工具过重）

---

## 问题 10 ⭐ 轻微：§26 的目录树与「core 目录不依赖 Electron」的矛盾

**现象**：§26 推荐的结构把 `reminder/` 和 `notification/` 都放在 `core/`，但 `notification` 天然要调用 Windows 通知 API（Electron 依赖）。

**方案**：`core/notification` 只保留**确定发什么、要不要发、发过没有**（纯逻辑 + 数据库），真正「怎么发」拆到 `services/`。这样 `core/` 可以 100% 单元测试，也便于未来换壳。详见《00-架构设计》§2。
